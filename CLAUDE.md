# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

`npm start`/`npm run dev`/`npm install` all regenerate the Prisma client automatically (`postinstall`/`prestart`/`predev` scripts in `package.json`), so the client never drifts out of sync with `prisma/schema.prisma` after a `git pull` picks up a schema change. Only run `node app.js` directly (bypassing npm) if you've already generated the client yourself.

There is no test suite, lint config, or build step in this project. To verify a change boots correctly:

```bash
OPEN_BROWSER=false node -e "require('./app'); setTimeout(() => process.exit(0), 1500)"
```

Required env vars (see `.env`): `DATABASE_URL` (MySQL), `JWT_SECRET`. Optional: `PORT`, `NODE_ENV`, `OPEN_BROWSER`, `CLOUDINARY_URL` (required in production so uploads survive redeploys; `CLOUDINARY_FOLDER` overrides the root folder, default `kangsadan`), `GMAIL_USER`/`GMAIL_APP_PASSWORD` (Gmail App Password used to send password-reset emails via `config/mailer.js`; if unset, the reset link is logged to the console instead — fine for dev, must be set in production), `PUBLIC_BASE_URL` (base URL baked into stall QR codes/printed signs from `controllers/marketMapController.js`; defaults to the request's protocol+host — set it if production sits behind a proxy or a different domain).

**Production-only:** set `ENABLE_LAPSED_RELEASE=true` on the production host only — it turns on the 5-minute job in `app.js` that releases stalls not renewed by 20:00 on their last selling day and restores stalls of unpaid lock-extension requests (`utils/stallRenewal.js`). Leave it unset locally: every dev machine points at the shared DB, so enabling it in dev would release real stalls. Timezone needs no env var — `config/timezone.js` forces `Asia/Bangkok` (required first in `app.js` and `utils/bookingRound.js`) because all round/deadline logic uses server-local time.

## Architecture

Server-rendered Express + EJS app ("Kangsadan Night Market" management system) backed by MySQL via Prisma. No frontend framework/bundler — views are `.ejs` templates in `views/`, static assets served from `public/`.

**Request flow (`app.js`):** two global middlewares run before routing: one sets `res.locals.path` (current URL, used by nav partials to highlight active links), one resolves `req.user`/`res.locals.user` via `getCurrentUser` (from `middlewares/jwtAuth.js`), so **every view has access to `user` even on public pages** — auth is not required to know who's logged in. Routers are mounted in this order:

- `/` → `routes/authRoutes.js` (login, register, logout, profile)
- `/admin` → `routes/adminRoutes.js` (dashboard, announcements, users, approvals, requests, bookings) — gated by `isStaffOrAdmin` (and `isAdminOnly` for user management specifically)
- `/` → `routes/sellerRoute.js` (zone selection, repair reports, stall booking, and the market map `/market-map` + its extras `/market-map/{qr,sign,print,track}` handled by `controllers/marketMapController.js`)

**`/market-map` is public (no login)** so customers can scan a stall's QR sign. Internal data (vacancy, contract end dates, inspection results, lot prices, open repairs) is stripped server-side by role in `getMarketMapPage` — never just hidden with CSS. Its client is split into `public/js/marketMap.js` (map, layers, cards) and `public/js/marketNav.js` (step-by-step navigation, loaded after and reusing marketMap.js globals).

A catch-all 404 handler re-renders `index` with an error message rather than a dedicated error page.

**Auth model — two parallel middleware layers, both reading the same JWT:**
- `middlewares/jwtAuth.js`: `requireAuth` is the hard gate (401 JSON if the URL/`Accept` header implies an API call, otherwise redirect to `/login`). It also exports `getCurrentUser`, which reads the JWT from the `Authorization: Bearer` header or the `token` cookie and is soft (returns `null` instead of failing) — used for the global `res.locals.user` middleware in `app.js`.
- `middlewares/auth.js`: role gates (`isStaffOrAdmin`, `isAdminOnly`) built on top of `getCurrentUser`, used to protect `/admin/*` routes.
- `config/authSecrets.js` centralizes the JWT secret and cookie options (httpOnly, sameSite=lax, secure only in production) and throws if `JWT_SECRET` is missing in production (falls back to a dev-only secret otherwise).
- `middlewares/authRateLimit.js` defines per-endpoint rate limiters (`authLimiter`, `registerLimiter`, `forgotPasswordLimiter`) applied in `authRoutes.js`.

Routes that need JSON vs. HTML behavior (login/register/forgot-password) branch on whether `req.originalUrl` starts with `/api/` or `Accept: application/json` is set — the same controller handles both a form POST (`/login`) and its API twin (`/api/auth/login`).

**Data layer:** `prisma/schema.prisma` defines the models: `User` (role enum: ADMIN/STAFF/SELLER/CUSTOMER), `ShopDetail` (1:1 with User), `Slot`/`Booking` (market stall booking), `BookingRequest` (owner = `userId` → `User`; `sellerId`/`Seller` is a dead table that is never populated — don't use it, and never match requests to users by `sellerName`), `MaintenanceReport` (repair requests, status enum: PENDING/APPROVED/REJECTED/IN_PROGRESS/SUCCESS), `Announcement` (targeted by `targetRole`/`targetRoles`). `EventBoothRequest` (event-booth requests for zone G — `userId` is optional because guests can submit; status flow PENDING → IN_PROGRESS (approved, awaiting payment) → SUCCESS / REJECTED). Only `User` has a hand-written data-access module (`models/userModel.js`, which also strips `password` via `sanitizeUser` before returning users to callers) — other models are queried directly from controllers/routes via `new PrismaClient()`.

**Controllers** (`controllers/`) hold the actual route logic; routers mostly just wire path + middleware + controller method. `controllers/auth.js` is an empty leftover file — `controllers/authController.js` is the real auth controller.

**Event booths (zone G, `EVENT_BOOTH`):** two booths, G101 (under the F1/F2 rows) and G201 (under F5/F6, next to zone B), at 490 baht/day (`utils/lotPricing.js`). They are **not** booked through `/select-zone` → `/booking-stall` (zone G redirects to `/event-booth`), and `confirmBookingStall` refuses to assign them to a seller's request. Anyone can request one at `/event-booth` without logging in, then track it and upload the payment slip at `/event-booth/track/:trackingToken`. Admins/staff handle requests at `/admin/event-booths` (it has its own navbar badge). Whether a booth is free comes only from `EventBoothRequest` rows covering that day (`utils/eventBooth.js`, read by `buildZonesData` and `utils/stallDayStatus.js`) — `Stall.status` is never set to BOOKED for event booths. The overview map draws zone G as two blocks (`#zone-G1`/`#zone-G2` with `data-zone="G"`; JS reads the zone through `zoneOfBlock()`). In zone F's grid, the event areas are `PLACEHOLDER` cells with an `eventLink` property, so stall counts skip them. Add zone G to the DB with `node prisma/fixes/2026-10-26-add-event-zone-g.js` (upsert only, safe to re-run).

**Rental statements & documents:** `utils/rentalStatement.js` builds multi-round rent/payment reports in batch (one row per `BookingRequest` with a stall assigned — SUCCESS = paid, IN_PROGRESS = outstanding). It reads money from the **first** linked `Booking` only, because every `Booking` row of a request stores the whole request's totals; it resolves the owner as `BookingRequest.userId ?? Booking.userId`. Sellers see `/rental-statement`; admins only (`isAdminOnly`, the pages show ID-card numbers) see `/admin/rental-statements` (+ `/user/:id`, `/stall/:code`). Date fields use the same custom calendar as stall booking (`public/js/common/datePicker.js`). **Document requests** live together but on separate pages: sellers pick at `/documents` → `/documents/tax-invoice` (the form moved out of `/shop-profile`, partial `taxInvoiceRequestCard.ejs`) or `/documents/lease-contract`; admins pick at `/admin/documents` → `/admin/tax-invoice-requests` or `/admin/lease-contracts`. The `documentSwitch` partial is the tab bar between the two. **Lease contracts** are generated, not uploaded: the seller picks a date range (it must contain paid rentals) → `utils/leaseContract.js` builds the contract live from paid bookings in that range → the admin reviews the draft and approves (assigns `documentNumber` L{yyyymm}/{id}) or rejects with a reason → the seller opens/prints it at `/lease-contracts/:id`. Once issued, only bookings paid before `issuedAt` count, so the contract doesn't change afterwards. Clause wording lives in `utils/leaseContractTemplate.js` (a standard draft — have the market owner review it).

**Shop reviews (`ShopReview`):** members only — logged-in `CUSTOMER`/`SELLER`. The shop owner, ADMIN and STAFF can't review. One review per member per shop; posting again updates the existing one and clears the shop's earlier reply. Reviews belong to the shop owner (`shopUserId`), not the stall code, so they follow the shop when it moves stalls. The owner is resolved from the stall code with `getStallOwnerIndex` (`utils/shopViews.js`), so it depends on `BookingRequest.userId` being filled in (run the backfill script). Anyone can read reviews via `GET /shop-reviews/:code` on the market-map card and the `#reviewViewer` window; posting goes to `POST /shop-reviews/:code` (`routes/reviewRoutes.js`). Sellers reply to or report reviews in the "รีวิวร้านคุณ" section of `/shop-profile` (they can't delete them). Admins/staff hide or unhide reviews at `/admin/shop-reviews`; a hidden review isn't shown and isn't counted in the average. All rules live in `utils/shopReviews.js`. Extras: `/market-map?stall=X&reviews=1` opens the review window directly (used by the second QR on the A5 sign and by the login redirect); `/login?next=<path>` returns to that page after login (only internal paths pass `safeNextPath` in `authController.js`; `?tab=register` opens the register tab); the seller bell shows "มีรีวิวร้านใหม่" while there are unreplied reviews from the last 14 days (`buildReviewNotifications`, computed live, no read-state table); stall cells in the category layer show a "★4.7" badge for shops rated 4+ (hidden when the "ปิด" badge is showing).

**File uploads** use `multer` with the custom storage engine in `utils/imageStorage.js` (`createImageStorage({ folder, prefix })`). If `CLOUDINARY_URL` is set, files go to Cloudinary and the DB stores the full `https://res.cloudinary.com/...` URL; if unset (dev), it falls back to `public/uploads/<folder>/` and stores `/uploads/...`. Always read `file.url` (never build the path from `file.filename`), delete old images via `deleteImage(url)`, and read images back via `readImageBuffer(url)` (used by slip verification). Legacy announcement rows store only a filename — views use the global `imageUrl(value, 'announcements')` helper. `node scripts/migrate-uploads-to-cloudinary.js [--apply]` moves existing local files and DB values to Cloudinary. Registration's `productImage` field still uses in-memory `multer()`.

**Lock renewal (ต่อล็อก):** rules (when renewal opens, the 20:00 cutoff on the last selling day, no renewing past the round end) live in `utils/stallRenewal.js`. Renewing keeps the seller's **same stall without admin approval or re-assignment**: `POST /booking-stall/extend` checks the stall is still `BOOKED` with the old end date, then creates the `[EXTEND_OF:<id>]` request directly as `IN_PROGRESS` (with `assignedStallCode`, `lockAssignedAt`, `paymentDueAt`), creates `IN_PROGRESS` `Booking` rows at the old contract's prices, and extends `Stall.bookingEndDate` immediately. The admin only confirms the slip as usual. If it isn't paid in time, `restoreUnpaidExtensions` (production job) puts the old end date back. The seller can renew straight from the "ต่อล็อกไหม?" card (and the admin's "แจ้งเตือนร้านค้า" card) on `/notifications`: the entry carries `renew` (`buildRenewQuote`: full round, holidays excluded via `getBillableDays`), and `notifications.js` renders it as an inline form that posts `newEndDate` = round end. "เลือกวันเอง" goes to `/booking-stall/extend` for shorter renewals.

**Navbars:** `views/partials/navbar.ejs` (ADMIN/STAFF), `navbarSeller.ejs`, `navbarCustomer.ejs` (also guests: shows only public links + a login button) share one layout: main links + a "เพิ่มเติม" `<details class="nav-dropdown">` + bell + account dropdown, all in one row on desktop (icons hide at 993–1239px so it still fits). The account dropdown (profile / switch view / logout) is `partials/navAccount.ejs`; the shared styles are `public/stylesheets/partials/navMenu.css` (classes `nav-v2__*`, on top of `navbar.css`). Each partial lists its links as arrays at the top. Add a menu item there, and if it's secondary put it in `moreLinks`, because the desktop row is full. On mobile, `moreLinks` are rendered again as flat `nav-v2__mobile-only` items in the hamburger menu, the bell sits next to the hamburger (`.nav-v2__bell`, two bells exist, so `syncBell` in `notifications.js` updates both), and the admin hamburger shows the total pending-work count.

**Localization:** UI copy, error messages, and code comments are primarily in Thai.

## Team conventions

This project is worked on by multiple people in parallel (branches per person: `tan`, `bow`, `tannav`, ...). To keep everyone's work compatible:

- **Branches:** work on your own branch (named after you), merge into `main` via PR — don't commit directly to `main`.
- **Commits:** one commit per logical change, message in Thai, written as a full sentence describing what changed (e.g. `เพิ่มระบบแอดมินตรวจสอบสลิปโอนเงินก่อนยืนยันล็อก`) — not `feat:`/`fix:` prefixes, not English.
- **Before starting work:** `git pull` on `main` and rebase/merge it into your branch first — several people touch `views/`, `controllers/`, and `routes/` at once, so stale branches conflict often.
- **UI/design:** follow the existing "gridgeist" visual style already applied across `index`, `admin`, and `seller` pages (see git history for `รีดีไซน์...เป็นสไตล์ gridgeist`) — sharp grid layout, visible borders, no `rounded-pill`/`rounded-4`. Use the `gridgeist` skill when redesigning or adding pages so new screens match — it's committed at `.claude/skills/gridgeist/` (MIT, from github.com/ohmiler/gridgeist), so Claude Code loads it for everyone automatically; update it there rather than installing a personal copy. **Fonts:** `Inter` for English/numbers and `Prompt` for Thai — load both with the same Google Fonts link every page uses (`family=Inter:wght@300;400;500;600;700&family=Prompt:wght@300;400;500;600;700`) and use one stack everywhere (including `--mono` and numbers/codes/dates): `'Inter', 'Prompt', -apple-system, BlinkMacSystemFont, 'Segoe UI', 'Leelawadee UI', Roboto, 'Sukhumvit Set', 'Noto Sans Thai', sans-serif`. `'Inter'` must come **before** `'Prompt'`: Inter has no Thai glyphs so Thai falls through to Prompt, but Prompt has its own Latin/digits so putting it first would mean Inter is never used. Numbers line up in tables because `font-variant-numeric: tabular-nums` (plus `-webkit-font-smoothing: antialiased`) is set on `html` in `partials/navbar.css` and `responsive.css`.
- **After schema changes:** run `npx prisma generate` and commit the migration under `prisma/migrations/` — don't hand-edit the generated client.
- **Applying schema changes to the shared DB (TiDB Cloud):** never use `prisma migrate dev` — the shared DB has drift unrelated to your change, so it prompts for `migrate reset`, which **wipes all team data**. Instead: check the diff first with `npx prisma migrate diff --from-url "$DATABASE_URL" --to-schema-datamodel prisma/schema.prisma --script` (must contain only your change), save it as `prisma/migrations/<timestamp>_<name>/migration.sql`, apply with `npx prisma db execute --file <that file> --schema prisma/schema.prisma`, then `npx prisma migrate resolve --applied <name>` so migration history matches the DB.
- **Before opening a PR:** boot-check the app (see verify command above) and click through the flow you changed in a browser; there's no automated test suite to catch regressions.
- **Language:** keep new UI copy, flash/error messages, and comments in Thai to match the rest of the codebase; code identifiers (variables, functions, routes) stay in English.
